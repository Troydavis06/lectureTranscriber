# Lecture Transcriber

**Play a lecture. Get the transcript. Nothing else to do.**

Watches Chrome for a lecture video, records exactly what you hear, and transcribes
it on your GPU the moment it finishes. No uploads, no API keys, no clicking record.

Lecture recordings are rarely captioned, and when they are the captions are usually
auto-generated by whoever hosts them and no better than what you could run yourself.
Meanwhile you already have a GPU sitting idle while you watch. This points it at the
problem: play the video as you normally would, and a timestamped transcript appears
when it ends.

---

## Quick start

```bat
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Then, each time you want to use it:

```bat
rem 1. Start the daemon and leave the window open.
run.cmd

rem 2. Start Chrome from here, not from the taskbar.
launch_chrome.cmd
```

Open a lecture and press play. That is the whole workflow.

> `launch_chrome.cmd` uses a **dedicated Chrome profile**, because Chrome 136+ refuses
> `--remote-debugging-port` on your default one. The first time you use it, sign in to
> your course site in that window. Your normal Chrome is untouched, and the daemon can
> be started before Chrome — it waits.

## What it does

### Starts and stops on its own

The daemon polls Chrome over the DevTools Protocol for the longest `<video>` on each
page. When one plays for two consecutive polls, recording begins; when it ends, the
transcription queue picks it up. Short clips, embedded promos and music sites are
filtered out before anything is recorded.

### Records what you hear, not what a microphone hears

Capture is WASAPI loopback, tapped off the render endpoint. That means headphones are
fine, no "Stereo Mix" device is needed, and nothing in the room gets picked up.

### Survives you pausing to think

Pausing the video pauses the recording; resuming resumes it. Paused time is never
written, so a lecture you stopped twice does not come back with two silent gaps in it.
Only a pause longer than `pause_grace_sec` (default two minutes) counts as the end.

### Timestamps that actually match the video

Detection needs a couple of polls to debounce, so recording starts a few seconds into
playback. That offset is measured and added back, and silence is padded where the
loopback endpoint delivers no frames at all. A `[12:04]` in the transcript is `12:04`
in the player, so you can scrub straight to anything worth rewatching.

### Keeps the GPU to itself

Transcription runs as a subprocess. CTranslate2 does not reliably hand VRAM back
inside a live process, so a long-lived daemon that imported it would hold a model's
worth of VRAM between lectures. Process exit is the only real guarantee — and it also
means a crash in the CUDA stack cannot take the daemon down with it.

### Never leaves the machine

Whisper runs locally against local files. There is no API key, no account, and nothing
is uploaded — the only network access in the whole tool is Hugging Face serving the
model the first time you run it, after which it works with the network off entirely.
Your recordings and transcripts stay in `data/`, which is gitignored.

## What comes out

Each lecture produces a readable `.txt` and a machine-readable `.json` in
`data/transcripts/`, both named after the lecture and the time it was recorded:

```
========================================================================
Lecture 7 - Dynamic Programming
2026-09-16 14:30 | 52 min | https://example.edu/lec7
========================================================================

[00:12] to continue our discussion from last week, we had just shown that
[00:20] the greedy choice fails here, and the reason it fails is worth being
[00:26] precise about, because it tells you exactly when to reach for a
[00:31] dynamic programming formulation instead
```

The JSON carries the same thing with the lecture metadata and per-segment start and
end times, for anything you want to build on top.

Re-transcribing a recording **replaces** that lecture's transcript rather than writing
a second copy, so changing the model and re-running is safe.

## Configuration

Every value has a default in `lecturetool/config.py`, so `config.toml` only needs the
keys you actually want to change. The ones worth knowing:

| Key | Default | Why you'd change it |
|---|---|---|
| `whisper.model` | `large-v3-turbo` | `large-v3` is slower and better with difficult accents |
| `whisper.compute_type` | `float16` | `int8_float16` if you are short on VRAM |
| `whisper.device` | `cuda` | `cpu` works — pair it with `compute_type = "int8"` and expect roughly realtime instead of 60x |
| `whisper.language` | `en` | Empty string to auto-detect per lecture |
| `chrome.pause_grace_sec` | 120 | How long a pause can last before the lecture is considered over |
| `chrome.min_video_duration_sec` | 120 | Ignore short clips and embedded promos |
| `chrome.url_denylist` | music/streaming hosts | Stop a non-lecture tab starting a recording |
| `chrome.url_allowlist` | `[]` | If set, **only** these hosts can start a recording |
| `audio.min_lecture_sec` | 180 | Discard recordings shorter than this |
| `audio.keep_recordings_days` | 7 | WAV retention; `0` keeps them forever |

## Models

| Model | VRAM | Speed |
|---|---|---|
| `faster-whisper large-v3-turbo` (float16) | ~1.6 GB | A 21-minute lecture in ~20 s on an RTX 4080, model load included |

Changing it is one line in `config.toml`. The model downloads itself on first use.

## Developing

Each stage runs on its own, which is how to diagnose anything:

```bat
rem Is system audio being captured at all? Play something, then:
.venv\Scripts\python.exe -m lecturetool.audio_capture --test 10
.venv\Scripts\python.exe -m lecturetool.audio_capture --list

rem What does the watcher see? Play and pause a video, and watch the events.
.venv\Scripts\python.exe -m lecturetool.chrome_watch --watch

rem Transcribe a file directly, bypassing Chrome entirely.
.venv\Scripts\python.exe -m lecturetool.transcribe data\recordings\x.wav

rem Unit checks. No GPU and no Chrome needed.
.venv\Scripts\python.exe tests\test_units.py
```

| Command | What it does |
|---|---|
| `run.cmd` | Run the daemon |
| `run.cmd --process <wav>` | Transcribe a saved recording, e.g. one left queued at shutdown |
| `run.cmd --process <wav> --title "Real Name"` | Same, with a nicer heading than the filename gives |
| `run.cmd -v` | Verbose logging |

| Module | Responsibility |
|---|---|
| `chrome_watch.py` | CDP polling, and the state machine that turns it into start/pause/resume/end |
| `audio_capture.py` | WASAPI loopback recorder, with pause/resume and drift padding |
| `transcribe.py` | faster-whisper, and writing the finished transcript |
| `writer.py` | Transcript formatting and atomic output |
| `__main__.py` | The daemon: wires events to the recorder and the transcription queue |

> `cuda_paths.py` registers the pip-installed cuDNN/cuBLAS DLL directories before
> CTranslate2 loads. If you see `Could not locate cudnn_ops64_9.dll`, run
> `.venv\Scripts\python.exe -m lecturetool.cuda_paths` to see what got registered.

## When it doesn't work

| Symptom | Usually |
|---|---|
| No transcript ever appears | The recording was under `audio.min_lecture_sec`, or the captured audio was silent because Chrome is playing through a device that is not the Windows default output. `audio_capture --test 10` settles the second one. |
| `Chrome is not reachable on port 9222` | Chrome was started normally rather than via `launch_chrome.cmd`. |
| Nothing starts recording | Run `chrome_watch --watch`. A video showing `skip` is being filtered — most likely shorter than `chrome.min_video_duration_sec`, or its host is in `url_denylist`. |
| `Could not locate cudnn_ops64_9.dll` | The pip NVIDIA packages are missing. Re-run the install, then check `-m lecturetool.cuda_paths`. |
| Transcript timestamps drift from the video | The player seeked without Chrome reporting it. Timestamps are anchored to the position at which recording started, so scrubbing mid-lecture is not tracked. |

## Honest limitations

- **Windows only.** Loopback capture is WASAPI, and the launcher is a `.cmd` file.
  The Chrome and Whisper halves are portable; the audio half is not.
- **Chrome only**, and only Chrome started by `launch_chrome.cmd`. Firefox and Safari
  have no equivalent of the DevTools Protocol endpoint this relies on.
- **One lecture at a time.** Loopback captures the whole output device, so a second
  video playing alongside would land in the same recording. Whichever qualifying video
  starts first owns the recorder until it finishes.
- **It records your speakers.** Anything else making noise — a notification, a message
  tone — ends up in the audio and possibly in the transcript.
- **Whisper is not a stenographer.** Expect trouble with dense notation, names, and
  anything said over a bad connection. Equations come out as spoken, not as LaTeX.
- **Speakers are not separated.** A seminar with heavy discussion reads as one
  continuous stream, with no indication of who is talking.
- **GPU strongly recommended.** CPU transcription works and is roughly realtime, which
  defeats most of the point.
